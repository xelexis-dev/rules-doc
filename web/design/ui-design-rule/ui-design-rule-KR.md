# UI Design Rules

웹 개발 프로젝트에서 디자이너·개발자·AI 에이전트가 함께 사용하는 UI 설계 및 검증 규칙이다.

## 1. 적용 범위와 우선순위

- **적용 대상:** 웹 페이지, 재사용 컴포넌트, 디자인 토큰, 색상과 테마를 변경하는 작업.
- **필수:** 구현 및 리뷰에서 충족해야 하는 규칙이다.
- **권장:** 화면의 목적과 기존 디자인 시스템에 맞게 조정할 수 있는 지침이다. 다른 방식을 선택했다면 이유를 기록한다.
- 기존 프로젝트의 명시적인 요구사항, 디자인 시스템, 컴포넌트와 토큰 명명 규칙을 먼저 확인한다. 이 문서는 기존 규칙에서 정하지 않은 부분의 기본값으로 사용한다.
- 기존 스타일을 재사용할 때도 접근성 기준을 확인한다. 브랜드 색상이나 기존 구현이라는 이유만으로 대비 실패를 그대로 유지하지 않는다.
- 이 문서의 대비 기준은 WCAG 2.2의 관련 AA 성공 기준을 따른다. 이 문서만으로 WCAG 전체 준수를 보장하지는 않는다.

## 2. 작업 전 확인 — 필수

1. 프로젝트의 `AGENTS.md`, UI 문서, 공통 스타일, 토큰 정의, 관련 컴포넌트를 읽는다.
2. 기존 팔레트, 의미 기반 토큰, 테마 적용 방식, 지원하는 화면 크기를 확인한다.
3. 작업 대상에 필요한 상태를 정한다. 예: 기본, hover, focus-visible, pressed, selected, disabled, loading, error.
4. 동일한 역할의 컴포넌트나 토큰이 있으면 재사용한다. 이름만 다른 중복 토큰을 만들지 않는다.
5. 토큰 체계가 없는 프로젝트는 공통 정의 위치를 하나 정하고 문서화한다. 특정 라이브러리나 색상 계열을 임의로 강제하지 않는다.

## 3. 색상 팔레트

### 필수

- 색상은 일관된 단계와 사용 목적을 가진 팔레트로 관리한다.
- 기존 팔레트를 우선 사용하고, 필요한 밝기나 역할을 충족하지 못할 때만 확장한다.
- 신규 팔레트는 밝은 색부터 어두운 색까지 필요한 명도 범위를 준비한다. 단계 이름과 순서를 일관되게 유지한다.
- 색상 단계의 번호만으로 가독성을 판단하지 않는다. 실제 전경색과 배경색의 조합을 검사한다.
- 특정 팔레트의 모든 단계를 사용하거나 생성하도록 강제하지 않는다.

### 권장

- 배경·표면에 사용할 중립색과 브랜드·상태를 표현할 색상을 구분해 구성한다.
- 기존 규칙이 없다면 `50`, `100`, …, `900`, `950`처럼 순서를 파악하기 쉬운 체계를 고려한다. 이는 선택 가능한 명명 예시다.

## 4. 의미 기반 색상 토큰 — 필수

- 색상의 실제 값과 UI에서 맡는 역할을 분리한다.
- 컴포넌트는 역할에 맞는 의미 기반 토큰을 참조한다. HEX·RGB·HSL 등의 실제 UI 색상 값을 개별 컴포넌트에 반복해서 하드코딩하지 않는다.
- 실제 색상 값은 공통 팔레트·토큰 정의에서 관리하고, 의미 토큰을 해당 값에 연결한다.
- 기존 시스템이 CSS 변수, 테마 객체 또는 유틸리티 클래스를 사용한다면 그 방식을 유지한다. 같은 의미를 표현하는 별도 체계를 추가하지 않는다.
- 텍스트·아이콘에 필요한 전경 토큰은 함께 사용할 배경 토큰과 조합해서 검증한다. 브랜드 색상 위의 글자를 무조건 흰색으로 정하지 않는다.
- 차트의 데이터별 색상처럼 역할이 다른 영역은 해당 영역의 팔레트 규칙을 정의한다. 예외가 필요한 외부 콘텐츠나 자산은 범위와 이유를 기록한다.

다음 이름은 역할을 설명하는 예시다. 기존 프로젝트의 토큰을 일괄적으로 바꾸라는 지시가 아니다.

| 역할 | 토큰 이름 예시 | 사용 목적 |
| --- | --- | --- |
| 페이지 배경 | `bg.canvas` | 화면 전체의 기본 배경 |
| 표면 배경 | `bg.surface` | 카드, 패널, 팝업 등의 표면 |
| 주요 텍스트 | `text.primary` | 제목과 본문 등 핵심 정보 |
| 보조 텍스트 | `text.secondary` | 설명과 부가 정보. 대비 기준은 별도로 충족해야 함 |
| 브랜드 | `brand.primary` | 브랜드를 나타내는 색상 |
| 주요 동작 | `action.primary.bg` / `action.primary.fg` | 주요 버튼의 배경과 전경 |
| 오류 | `status.error` | 오류 메시지와 상태 표시 |
| 구분선·경계 | `border.default` | 요소를 구분하는 선 |
| 키보드 포커스 | `focus.ring` | 현재 키보드 조작 대상 표시 |

## 5. 배색과 시각적 위계 — 권장

**60:30:10**을 배색의 출발점으로 활용한다.

| 비중 | 역할 | 적용 방향 |
| --- | --- | --- |
| 약 60% | 중립적인 주조색 | 넓은 배경과 기본 표면 |
| 약 30% | 보조색 | 영역 구분과 보조적인 시각 요소 |
| 약 10% | 강조색 | 주요 동작과 중요한 정보 |

- 이 비율은 시각적 균형을 위한 참고 지침이다. 픽셀 면적이나 DOM 요소 수로 정확한 비율을 강제하지 않는다.
- 강조색은 우선순위가 높은 정보와 동작에 집중한다. 여러 요소를 같은 강도로 강조해 위계가 사라지지 않도록 한다.
- 오류·경고·성공 상태의 의미와 가독성은 장식적인 배색 비율보다 우선한다.
- 데이터 시각화, 브랜드 중심 화면 등은 목적에 맞게 비율을 조정할 수 있다.

## 6. 명암 대비와 상태 표현 — 필수

### 대비 기준

| 대상 | 최소 대비 | 검사할 색상 조합 |
| --- | --- | --- |
| 일반 텍스트 및 텍스트 이미지 | **4.5:1** | 텍스트와 실제 배경 |
| 큰 텍스트 및 해당 텍스트 이미지 | **3:1** | 텍스트와 실제 배경 |
| 컨트롤과 상태를 식별하는 데 필요한 시각 정보, 내용 이해에 필요한 그래픽 | **3:1** | 식별에 필요한 부분과 인접 색상 |

큰 텍스트는 일반적으로 **18pt 이상 또는 굵은 14pt 이상**을 의미한다. CSS 기준으로 약 24px 또는 굵은 18.67px에 해당하며, 실제 글꼴과 렌더링 크기를 확인한다. 큰 텍스트에 해당하는지 불분명하면 4.5:1을 적용한다. 텍스트 기준과 예외는 [W3C의 Contrast (Minimum) 설명](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)에 따른다.

비텍스트의 3:1은 모든 장식선에 일괄 적용하는 조건이 아니다. 컨트롤·상태·정보를 식별하는 데 필요한 시각 요소를 대상으로 한다. 기본 상태와 hover 상태 사이의 색 차이를 3:1로 만들라는 의미도 아니다. 각 상태에서 식별 요소와 인접 색상을 비교한다. [W3C의 Non-text Contrast 설명](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

### 검사 방법

- 계산된 대비 수치를 기준으로 판정한다. 4.499:1을 반올림해서 4.5:1 통과로 처리하지 않는다.
- 보조 텍스트, placeholder, 버튼 레이블, hover·focus 시 표시되는 텍스트도 해당 기준을 검사한다.
- 투명도, 그라데이션, 이미지가 포함된 배경은 실제 합성 결과에서 대비가 가장 낮아지는 부분을 확인한다.
- 구현한 테마와 관련 상호작용 상태별로 확인한다. 기본 화면 한 장의 검사로 전체 상태가 통과했다고 판단하지 않는다.
- 자동 검사로 판단할 수 없는 조합은 계산 도구와 화면 검토로 보완하고, 확인하지 못한 항목을 기록한다.

### 예외와 상태 표현

- 비활성 컨트롤, 순수 장식, 로고 등에는 해당 성공 기준의 예외가 있다. 예외 적용 시 대상과 근거를 기록한다. 단순히 연하게 표시한 보조 정보는 예외로 취급하지 않는다.
- 오류·성공·선택 여부를 색상만으로 전달하지 않는다. 텍스트, 아이콘, 형태 또는 명확한 상태 표시를 함께 사용한다.
- 키보드 포커스는 눈에 보이게 유지한다. 기본 outline을 제거할 때는 식별 가능한 대체 표시를 제공한다.

## 7. 라이트·다크 테마 — 지원하는 프로젝트에 필수

- 동일한 의미 토큰을 유지하고 테마별로 연결되는 색상을 변경한다.
- 컴포넌트에 테마별 실제 색상 값을 반복해서 작성하지 않는다. 기존 토큰·테마 계층에서 매핑을 관리한다.
- 색상 전체를 기계적으로 반전하는 방식으로 테마 구현을 완료했다고 판단하지 않는다.
- 배경, 표면, 텍스트, 테두리, 브랜드 전경, 상태색, 포커스 표시를 각 테마에서 검증한다.
- 관련 컴포넌트의 hover, focus-visible, selected, disabled, loading, error 등 구현된 상태도 확인한다.
- 이미지, 로고, 차트처럼 테마에 영향을 받는 자산은 각 테마에서 식별 가능한지 확인한다.
- 테마 선택 저장과 시스템 설정 반영은 프로젝트의 기존 정책을 따른다. 정책이 없고 새로 구현해야 한다면 동작을 정해 문서화한다.
- 단일 테마 프로젝트에 다크 모드를 임의로 추가하지 않는다. 현재 지원하는 테마 범위에 이 규칙을 적용한다.

## 8. 컴포넌트와 화면 구성

- **필수 — 컴포넌트:** 기존 버튼·입력·카드 등의 공통 컴포넌트를 우선 재사용한다. 같은 역할에 서로 다른 스타일을 무분별하게 추가하지 않는다.
- **필수 — 타이포그래피와 간격:** 기존 글자 크기, 굵기, 행간, 간격, 모서리 반경 체계를 따른다. 체계가 없다면 반복되는 값을 공통으로 정의한다.
- **필수 — 반응형 화면:** 프로젝트가 지원하는 작은 화면과 큰 화면에서 정보 순서, 줄바꿈, 겹침, 잘림, 조작 가능 여부를 확인한다.
- **필수 — 상태와 피드백:** 변경한 흐름에 필요한 로딩·빈 결과·오류·완료 상태를 제공한다. 오류는 발생한 위치와 해결 방법을 이해할 수 있게 표현한다.
- **필수 — 조작:** 가능한 경우 의미에 맞는 기본 HTML 요소를 사용하고, 관련 흐름을 키보드로 완료할 수 있는지 확인한다.
- **권장 — 장식과 모션:** 장식과 애니메이션은 정보 이해를 돕는 범위에서 사용한다. 새로운 효과를 추가하면 동작 감소 설정에서도 사용 가능한 표현을 제공한다.

## 9. 완료 전 검증

변경한 범위에 해당하는 항목을 확인한다. 적용되지 않는 항목은 이유를 기록한다.

- [ ] 기존 토큰과 컴포넌트를 확인하고 재사용했다.
- [ ] 새 색상 값은 공통 정의에서 관리하며, 중복 토큰과 불필요한 하드코딩을 추가하지 않았다.
- [ ] 의미 토큰의 역할과 실제 사용 위치가 일치한다.
- [ ] 일반 텍스트, 큰 텍스트, 의미 있는 비텍스트 요소의 적용 기준을 구분해 대비를 검사했다.
- [ ] 지원하는 테마와 변경한 컴포넌트의 관련 상태를 확인했다.
- [ ] 색상만으로 오류·성공·선택 상태를 전달하지 않는다.
- [ ] 키보드 포커스가 보이며 관련 동작을 키보드로 수행할 수 있다.
- [ ] 프로젝트가 지원하는 화면 크기에서 읽기와 조작에 문제가 없다.
- [ ] 프로젝트에 정의된 관련 검증 명령을 실행하고 결과를 확인했다. 명령은 실제 프로젝트 설정에서 확인한다.
- [ ] 검사하지 못한 항목, 기준 미달, 예외 사항을 완료 보고에 명시했다.

완료 보고에는 **변경한 컴포넌트와 토큰, 확인한 테마·상태·화면 크기, 대비 검사 결과, 실행한 검증과 미확인 사항**을 포함한다.

## 10. AGENTS.md에서 참조하는 방법

이 파일을 프로젝트 루트에 배치했다면 프로젝트의 `AGENTS.md`에 다음 지침을 추가할 수 있다. 파일 위치가 다르면 경로를 맞춘다. 중복 로딩을 피하도록 사용할 언어 버전 하나만 연결한다.

```md
## UI 작업 규칙

- UI를 생성하거나 수정하기 전에 프로젝트 루트의 UI_DESIGN_RULES.md를 읽고 적용한다.
- 기존 디자인 시스템과 토큰을 우선 재사용한다.
- UI_DESIGN_RULES.md의 완료 전 검증 항목 중 변경 범위에 해당하는 항목을 확인한다.
- 완료 보고에는 검증 결과와 확인하지 못한 항목을 명시한다.
```

프로젝트별 토큰 파일 위치, 지원 테마, 화면 크기, 검증 명령은 기존 프로젝트 문서에 기록한다. 이 파일 이름만으로 모든 도구가 자동으로 읽는다고 가정하지 말고, 사용하는 도구의 지침 문서에서 참조하도록 연결한다.
